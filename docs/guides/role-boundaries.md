# API 연동 — 퍼블리셔 · 프론트엔드 · 백엔드는 어디까지 하나

> 퍼블리셔에서 프론트엔드로 전향하며 "API 연동을 어느 수준까지 해야 하고, 어디부터 백엔드가 처리하는지"를 정리한 문서 (2026-10-06).
> 기준은 "퍼블리셔가 어디까지"가 아니라 **"프론트엔드 개발자로 인정받으려면 어디까지"**다.

---

## 1. 역할별 경계

| 영역 | 퍼블리셔 | 프론트엔드 (목표) | 백엔드 |
|---|---|---|---|
| 응답 데이터 모양(JSON) 이해 | 읽을 줄 앎 | 타입으로 정의·검사 | 설계·결정 |
| 상태별 화면 (로딩·에러·빈·성공) | 마크업·스타일 | **언제 무엇을 보여 줄지 로직까지** | — |
| 데이터 요청 (fetch) | 보통 안 함 | **필수** — 상태 코드 처리, 재시도, 취소 | — |
| 캐싱·중복 요청·새로고침 | — | **필수** — TanStack Query 등 | 캐시 헤더 정도 |
| 목 데이터·목 API | 정적 더미 | MSW·목 API로 백엔드 없이 개발 | — |
| 폼 입력 검사 | `required` 속성 | 사용자 경험용 검사, 에러 표시·포커스 | **최종 검사 (보안)** |
| 로그인 | 화면만 | 로그인 상태 유지, 막힌 페이지 처리, 토큰 다루기 | **인증·권한 판단** |
| API 만들기 | — | (Next.js 회사면 간단한 것) | **담당** |
| DB 설계·쿼리 | — | (보통 안 함) | **담당** |
| 비즈니스 규칙 (재고 차감, 결제, 쿠폰) | — | 화면 쪽 안내 | **담당** |
| 보안·성능·서버 운영 | — | 브라우저 쪽 보안(XSS 등) | **담당** |

**핵심 경계선**
- **프론트엔드:** 받은 데이터를 어떻게 **요청하고, 기다리고, 실패를 다루고, 보여 주는가**
- **백엔드:** 데이터가 **맞는지, 누가 봐도 되는지, 어떻게 저장되는지**

> 브라우저에서 하는 검사·막기는 "친절"이고, 서버에서 하는 검사·막기는 "보안"이다. 브라우저 코드는 누구나 고칠 수 있으므로, 같은 규칙이라도 서버에서 다시 검사해야 한다. (Step 8-3 Server Action에서 권한·입력값을 다시 검사한 이유)

## 2. Shoppr에서 한 것과 맞춰 보기

| 스텝 | 내용 | 실무 기준 |
|---|---|---|
| Step 3 스켈레톤, 4-3 로딩·에러 화면 | 상태별 화면 | 퍼블리셔도 하는 일 — 이미 강점 |
| Step 6-3 fetch 직접 처리 (`lib/api.ts`) | 상태 코드, 재시도, 취소 | **프론트 필수** — 면접 단골 |
| Step 7 TanStack Query | 캐싱, 중복 제거, 더 보기 | **프론트 필수** — 요즘 공고에 자주 나옴 |
| Step 6-4 MSW | 백엔드 없이 개발 | **프론트 우대** — 협업 경험으로 어필 |
| Step 6-1 Route Handler | API 만들기 | 경계 — Next.js 회사면 프론트가 하기도 함 |
| Step 8 Prisma, Server Actions | DB, 서버 쓰기 | **보통 백엔드 몫** — 대신 포트폴리오 차별점 |

- Step 6~7까지가 "프론트엔드라면 당연히 할 줄 알아야 하는" 범위.
- Step 8은 실무에서 맡을 일은 적지만, **백엔드가 무엇을 하는지 알기 때문에 협업을 잘한다**는 근거가 된다.

## 3. 실무에서 가장 많이 부딪히는 지점 — API 명세 협의

실무는 보통 백엔드가 만든 **API 명세**(Swagger 등)를 받아서 시작한다. 화면을 아는 프론트가 먼저 요구해야 할 것들:

| 요구할 것 | 왜 필요한가 | Shoppr에서 |
|---|---|---|
| 목록 응답에 **전체 개수·다음 페이지 여부** | 더 보기·페이지 번호 | `ProductListResponse`의 `total`·`nextPage` |
| 이미지 **크기(width·height)** | 이미지가 오기 전에 자리를 잡아 레이아웃 이동(CLS) 방지 | `image { src, width, height }`, 8-4에서 직접 잰 이유 |
| **에러 응답 모양 통일** | 화면에 띄울 문구를 한 방법으로 꺼냄 | `{ error: { message } }` (`lib/apiResponse.ts`) |
| **없음(404)과 고장(500) 구분** | 안내가 다름 (주소 확인 vs 잠시 후 다시) | 장바구니에서 404는 조용히 빼고, 500은 다시 시도 |
| **필터·정렬·나누기를 서버가** | 데이터가 많으면 브라우저에서 못 함 | Step 7-2·7-3에서 서버로 옮김 |
| 응답을 배열 대신 **객체로 감싸기** | 나중에 필드를 더해도 쓰는 쪽이 안 깨짐 | `{ items, total }` (`types/api.ts`) |

퍼블리셔 출신은 화면 상태와 레이아웃 이동을 잘 알기 때문에 **이런 요구를 먼저 꺼낼 수 있다** — 이게 강점이다.

## 4. 우선순위

1. **확실히 내 것으로**
   - fetch 에러 처리(상태 코드, 네트워크 끊김), 로딩·에러·빈 상태 설계, TanStack Query, TypeScript 타입
   - "직접 만들어 보고 문제를 겪어서 라이브러리를 도입했다"를 **숫자로** 말할 수 있으면 충분히 강하다 (같은 요청 2번 + 워터폴 3.7초 → 1.7초)
2. **알고는 있기**
   - 인증 흐름(토큰·쿠키·막힌 페이지), 서버 검사가 왜 꼭 필요한지 → Step 9
3. **맛보기로 충분**
   - DB 설계, SQL, 서버 운영. 깊게 파기보다 "왜 이렇게 나눴는지" 설명할 수 있으면 된다

---

## 5. 면접에서 말하기

> "API 연동은 요청·캐싱·에러 처리·상태별 화면까지 책임질 수 있습니다. 처음엔 fetch를 직접 다뤄 로딩·에러·취소·중복 방지를 구현했고, 같은 요청이 두 번 나가고 워터폴로 3.7초가 걸리는 문제를 발견해 TanStack Query 캐시로 1.7초로 줄였습니다.
> 백엔드 영역은 Prisma로 CRUD와 Server Actions를 직접 만들어 봐서, API 명세를 협의할 때 화면 쪽에서 무엇을 요청해야 하는지 압니다. 예를 들어 이미지 크기를 응답에 넣어 달라고 하면 레이아웃 이동을 막을 수 있습니다."
